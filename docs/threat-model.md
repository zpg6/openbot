# OpenBot threat model

- Scope: first read-only release with computation-only JavaScript
- Recorded: 2026-08-22
- Review owner: security owner
- Release status: design only, blocking probes remain open

## Security claim

An organization owner can confirm one short run that reads through one reviewed connector, calls one fixed model route, and may execute bounded JavaScript once in one disposable Cloudflare Sandbox. A candidate execution profile is synthetic-probe-only and never accepts a user run. An enabled, active profile also requires an unexpired signed Sandbox approval lease bound to the exact probe report, configuration, installation, environment, deployment, and check-set version. Its data classes and limits are narrowed by the organization policy, compute grant, Bot, and installation ceilings. Restricted and unknown data always deny. OpenBot grants only the capabilities in the signed manifest. A connection, Bot selection, model suggestion, raw probe report, runtime request, dispatch reservation, and sandbox process are never authority by themselves.

OpenBot does not claim universal resource scoping, vendor-side bearer revocation, exactly-once execution, provider business-data writes, a tamper-proof ledger, persistent Bot memory, shared computers, or safe arbitrary packages.

## Trust boundaries

| Component                     | Trusted for                                                                      | Not trusted for                                                              |
| ----------------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Browser                       | Presenting user input and returned views                                         | Identity, CSRF safety, account scope, authority, or output safety            |
| Control plane                 | Session handling, account-scoped use cases, safe views                           | Manifest signing, vendor capability decryption, or runtime execution         |
| Orchestrator                  | Policy reload, manifest signing, run lifecycle, vendor management                | Treating vendor create responses as unambiguous                              |
| Capability gateway            | Current authorization, reservation, request construction                         | Deciding policy beyond stored signed authority                               |
| Durable Object runtime        | Ordered orchestration and call-boundary journal                                  | Authorization, reusable credentials, or successful restart of uncertain work |
| Sandbox runner                | Request-digest check, fixed mechanical protocol, and matching Sandbox SDK method | Grant decisions, replay prevention, direct database access, or model intent  |
| Sandbox process               | Nothing                                                                          | Code, files, subprocesses, output, or compliance with instructions           |
| Metorial                      | Provider connection and filtered session execution                               | OpenBot account authority or connector-specific resource guarantees          |
| OpenRouter and model provider | Model inference and usage metadata                                               | Tool authority, route correctness before observation, or safe output         |
| D1                            | Durable control records within its documented behavior                           | Correct OpenBot concurrency SQL before deployed tests                        |
| Operator                      | Installation and key custody                                                     | Inability to alter the database, Worker, vendor account, or object storage   |
| Gate-attestation bootstrap    | Operator public-key registry, clock, signature verification, opaque decisions    | Accepting request-supplied trust or treating raw probe reports as authority  |

## Assets

- Browser sessions, passwords, bootstrap tokens, reset tokens, and CSRF secrets
- Organization membership, Bot revisions, catalog entries, grants, confirmations, manifests, and revocation fences
- Raw prompts, skill instructions, final answers, and future artifact bodies
- Metorial management keys, auth-config references, MCP URLs, and protocol state
- OpenRouter management keys, run-owned keys, requested route, resolved route, usage, and cost
- Manifest signing keys, encryption keyrings, keyed digest keys, event keys, and gateway tokens
- Run slots, gateway reservations, outbox rows, cleanup obligations, audit records, and evidence completeness
- Sandbox IDs, image digest, source code, input, output, process state, dispatch reservations, request digests, and destroy call results
- Installation jurisdiction and vendor destination disclosures

## Attackers

- A signed-out internet client
- An authenticated owner trying to cross an account boundary
- A compromised browser session or malicious site attempting CSRF
- Hostile prompt, skill text, model output, tool schema, tool result, or connector metadata
- Malicious JavaScript running inside the Sandbox
- A compromised or buggy Metorial provider or MCP server
- A model endpoint or router that resolves outside the requested route
- Duplicate, delayed, or reordered Queue delivery
- A stale Worker, Durable Object, or sandbox process after revocation
- An operator or database administrator with infrastructure authority
- A dependency or container-image supply-chain attacker

Hermetic D1 concurrency observations are hard-coded as non-authoritative and ineligible for attestation. They test SQL syntax, rollback, and error mapping only. Deployed proof requires two distinct writer deployments, a private non-deduplicating sink, fresh `first-primary` readback, and the blocked outcomes named in ADR 0009. Until that test runs, `control_store_unverified` and `gateway_reservation_unverified` remain active.

## Fail-closed code path

1. The control plane verifies an enabled, active execution-profile record, its immutable configuration digest, and its exact signed-attestation reference. It uses the bootstrap-owned registry, clock, installation context, and shared registry-generation reader to obtain an opaque generation-bound decision. Verification and final authorization deny if the current generation cannot be read or differs from the loaded registry. It then intersects profile, policy, grant, Bot, and installation classes and limits before creating a five-minute confirmation. A candidate, disabled, expired lease, reference mismatch, restricted input, or unknown input denies.
2. The orchestrator assigns a random run-owned Sandbox ID and receives one model code proposal through the run protocol.
3. The run-owned Durable Object asks the capability gateway to authorize and dispatch the code call using its run token and next sequence. The gateway checks the opaque decision and unexpired lease again for this authorization.
4. The gateway atomically consumes one stored reservation that binds the current run fence, sequence, digests, profile, and expiry.
5. The gateway calls its exclusive private `SandboxExecutionService.execute` binding with the consumed reservation ID, strict request object, and digest of its versioned canonical field projection. The protocol does not claim identity of pre- and post-RPC wire bytes.
6. The no-D1 runner recomputes the digest, checks the fixed execute protocol, creates the Sandbox, writes fixed files, and launches the reviewed argv once.
7. The runner streams bounded output. Success requires exactly one canonical JSON result whose bytes match the terminal digest. It cannot call kill or destroy through the execute entry point.
8. The orchestrator issues exact-handle kill under active-attempt authority when needed. It issues destroy under active-attempt or cleanup-obligation authority in every history. The runner reports `sdk_acknowledged`, `not_found`, or `outcome_unknown`; none claims independent destruction observation.
9. The orchestrator records the terminal state. An ambiguous dispatch, launch, process result, kill, or destroy response never retries code and never reports success.

## Operator limits

Self-hosting gives the operator Cloudflare, database, Metorial, and OpenRouter authority. The application cannot prevent that operator from changing Worker code, reading available secrets, altering database rows, or changing vendor settings. OpenBot's records make application behavior reviewable. They are not an external transparency log.

Workers Logs stay disabled until safe logging and sentinel tests pass. Even then, logs contain IDs, byte counts, durations, status codes, and stable errors only.

## Deferred threats

Provider business-data writes, R2 artifact bodies, shared collections, external database profiles, teams, schedules, browser automation, package installation, terminals, preview URLs, and persistent sandbox storage require their own updated rows before implementation. Their absence is a control in the first release, not unfinished UI.
